# 《微信 AI 打车助手》产品需求文档（PRD · 原型 v0.1）

> 一句话：用户不用打开打车 App，在微信里说一句「帮我叫辆车去机场」，AI Agent 通过 MCP 调用打车平台完成叫车。

**目标（结论先行）**：让「叫车」这件事从「打开 App → 输地址 → 选车型 → 下单」压缩成「微信里一句话」，核心成功标准是 **下单完成率** 和 **一次说清率**。

**成功标准（可验收）**：
- 一句话下达 → 发起订单，端到端 ≤ 30 秒。
- 首轮意图识别准确率 ≥ 95%（测试集）。
- 用户二次确认后下单成功率 ≥ 98%。

## 2. 范围与角色

**本期做**：微信文字/语音指令 → 意图识别 → 槽位填充 → MCP 查价 → 用户确认 → 下单 → 订单状态回传 → 取消/改目的地。
**本期不做**：拼车、代驾、企业发票自动报销、多平台自动比价下单（只做单一平台接入，先跑通链路）。

| 角色 | 是谁 | 关切 |
|---|---|---|
| 用户 | 微信里发起叫车的人 | 快、不用切 App、价格透明、别乱扣钱 |
| AI Agent | 负责理解与编排的智能体 | 意图准、槽位全、不乱调用工具 |
| MCP Server | 打车平台封装的标准工具接口 | 稳定、鉴权、限流 |
| 打车平台 | 提供车辆/司机/价格/订单 | 合规、防刷、结算 |
| 运营 | 后台看数据的人 | 转化率、失败原因、成本 |

## 3. 场景与需求清单

**场景（用户故事）**：
1. 用户 A：晚上赶高铁，手上提行李，语音说「帮我打车去高铁站，现在」。
2. 用户 B：文字说「叫个车从公司回家，下班高峰期，舒适型」。
3. 用户 C：订单已下，说「改目的地到国贸」。
4. 用户 D：价格太贵，说「算了，取消吧」。

**需求清单（每条可验收）**：

| ID | 需求 | 属性 | 优先级 | 验收点 |
|---|---|---|---|---|
| R1 | 文字/语音指令叫车 | 核心 | P0 | 指令可被识别并触发叫车流程 |
| R2 | 意图识别（叫车/查价/取消/改单） | 核心 | P0 | 四类意图准确率 ≥ 95% |
| R3 | 槽位提取（出发地/目的地/时间/车型） | 核心 | P0 | 缺槽位时主动追问，不瞎填 |
| R4 | MCP 查价并展示 | 核心 | P0 | 返回 1–3 档价格供选择 |
| R5 | 下单前二次确认 | 安全 | P0 | 无确认不产生订单，不可绕过 |
| R6 | 订单状态回传与推送 | 核心 | P1 | 司机接单/到达/上车节点可推送 |
| R7 | 取消/改目的地 | 核心 | P1 | 指令可正确路由到对应工具 |
| R8 | 兜底降级（无法理解/工具失败） | 防护 | P0 | 明确告知失败，不静默 |

## 4. 功能详述

### 4.1 核心链路

```
微信消息
  → Agent 意图识别（叫车/查价/取消/改单）
    → 槽位填充（出发地、目的地、时间、车型）
      → 缺槽位则追问（最多 2 轮）
      → MCP 工具调用 search_rides（查价）
        → 回显价格与选项
        → 用户确认「下单」
          → MCP create_order（下单）
          → 回执 + 订单跟踪（get_order_status 轮询/推送）
```

### 4.2 各功能点

**F1 意图识别**：把自然语言映射到 4 类意图 + 「闲聊/无关」。输出置信度，低于阈值走兜底追问，不硬猜。

**F2 槽位提取**：抽取出发地、目的地、时间、车型。规则：
- 出发地缺省 = 用户当前定位（需授权）。
- 目的地缺失 = 必须追问，**禁止**代填。
- 时间模糊（「一会儿」）= 追问或默认「现在」并明示。

**F3 MCP 工具层**（这是 MCP 的价值点，把平台能力标准化）：

| 工具 | 作用 | 关键参数 | 返回 |
|---|---|---|---|
| `search_rides` | 查价/查车 | 起终点、时间、车型 | 价格、时长、可用车 |
| `create_order` | 下单 | 车型、起终点、用户 token | 订单号、司机信息 |
| `get_order_status` | 查状态 | 订单号 | 状态枚举 |
| `cancel_order` | 取消 | 订单号、原因 | 是否成功 |
| `update_destination` | 改目的地 | 订单号、新目的地 | 是否成功 |

**F4 二次确认**（安全兜底的第一道闸）：`create_order`、`cancel_order` 这类「花钱/有后果」的工具，**必须**先给用户一个带金额的确认卡片，用户点「确认」才真正调用。Agent 无权限替用户直接下单。

### 4.3 模型约束（AI-native）

- **模型**：意图识别 + 槽位提取用 LLM；金额计算、订单状态用确定性逻辑（不交给模型）。
- **禁止幻觉**：价格、司机、时间等事实字段只能来自工具返回值，模型不得自行编造。
- **温度/采样**：下单类场景用低温度（减少随机性）；闲聊可放宽。
- **上下文**：单次会话上下文保留订单号，跨天会话不继承（避免串单）。

### 4.4 防护与兜底（核心问「模型出错了怎么办」）

| 出错情形 | 兜底 |
|---|---|
| 意图识别错（把「取消」听成「叫车」） | 有后果操作前必须确认；确认卡片里回显「将取消订单 XXX」 |
| 槽位填错目的地 | 下单确认卡片回显完整起终点，用户可见可改 |
| 工具调用失败/超时 | 明确提示「暂时叫不到车，请稍后再试」，并记录失败原因 |
| 模型输出无法解析 | 走规则兜底 + 转人工（引导用户用 App） |
| 重复下单/重复扣费 | 订单幂等：同一会话未完结订单不重复 create_order |
| 越权（替用户花钱） | create_order 强制二次确认，无「自动下单」开关 |

## 5. 非功能需求

- **性能**：意图识别 P95 ≤ 2s；MCP 调用 P95 ≤ 3s；端到端 ≤ 30s。
- **安全**：下单鉴权绑定用户身份；取消/改单需校验订单归属；接口全量 HTTPS。
- **合规**：定位授权明示同意；通话/支付留痕可审计；符合网约车信息留存要求。
- **数据需求（AI-native）**：
  - 训练/评测数据：标注的意图 + 槽位样本 ≥ 5000 条（含方言、口语）。
  - 反馈数据：每次「兜底转人工 / 用户纠正」都作为负样本回流。
  - 真实工具返回样本用于评测「模型是否忠实于工具结果」。

## 6. 验收标准（含 AI 评估标准）

**AI 评估标准（离线评测集）**：
- 意图识别准确率 ≥ 95%，槽位提取 F1 ≥ 90%。
- 「事实忠实度」≥ 99%：模型输出中的金额/时间/车牌必须与工具返回一致，逐字段比对。

**用例级验收（可验收）**：

| 用例 | 前置 | 操作 | 预期 |
|---|---|---|---|
| UC1 | 已授权定位 | 语音「打车去高铁站」 | 追问车型 → 回显价格 → 确认 → 生成订单 |
| UC2 | 未说目的地 | 「帮我叫车」 | 追问目的地，不代填 |
| UC3 | 已有订单 | 「改目的地到国贸」 | 调 update_destination，回显新目的地 |
| UC4 | 已有订单 | 「取消吧」 | 弹确认卡片，确认后订单取消 |
| UC5 | 工具故障 | 正常叫车 | 明确失败提示，不静默不卡死 |
| UC6 | 说「随便聊聊」 | 闲聊 | 识别为闲聊，不触发任何工具调用 |

## 7. 版本与遗留

**版本规划**：
- v0.1（本原型）：单平台、文字指令、基础四意图、二次确认。
- v0.2：语音优化、多车型比价、订单实时轨迹推送。
- v0.3：多平台接入、历史订单、发票。

**遗留问题（留痕可追溯）**：
1. 语音在嘈杂环境的识别率待真实环境验证。
2. 多平台比价时价格口径不一致，如何「比价后自动下单」暂不定。
3. 用户无打车平台账号时的绑定链路（微信授权 → 平台 token）需与平台方确认。

**埋点清单（AI-native）**：

| 埋点 | 用途 |
|---|---|
| 意图识别 top1 与置信度 | 监控识别质量 |
| 槽位缺失类型（缺出发地/目的地/时间） | 优化追问策略 |
| 工具调用成功/失败率、失败原因 | 平台稳定性 |
| 二次确认率、确认后完成率 | 安全成本 vs 体验 |
| 兜底转人工次数、用户纠正次数 | 负样本回流 |
