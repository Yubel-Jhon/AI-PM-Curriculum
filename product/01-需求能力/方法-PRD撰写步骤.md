# 方法 · PRD 撰写步骤（14 章 B 端 PRD 全流程）

> 沉淀自 skill `create-prd`。回答「怎么把分析好的需求写成一份可评审的 PRD」。
> 一句话定位：BRD 回答值不值、MRD 回答给谁、**PRD 回答做什么**、FSD 回答怎么做。

---

## 0. 产品定型（阶段 0）

动笔前先判两件事，它们决定各章节侧重：

### 商业属性（二选一）

| 属性 | 定义 | 典型 |
|---|---|---|
| 商业化产品 | 对外销售的软件（SaaS / 私有化 / 混合） | SaaS CRM、行业解决方案 |
| 企业自研系统 | 内部业务系统，不对外卖 | 内部 ERP、OA、运营后台 |

### 功能类型（四选一）

| 类型 | 特征 | 设计侧重 |
|---|---|---|
| 业务型管理软件 | 多角色协同、长业务链 | 流程、角色权限、数据建模、状态机 |
| 工具型软件 | 单一问题域、短业务链 | 效率、极简、快速上手 |
| 交易型平台 | 撮合交易、支付结算履约 | 交易闭环、支付、多边市场 |
| 基础服务型 | 抽象共享能力、供其他系统调用 | API 设计、稳定性、多租户 |

### 章节适配规则（摘要）

| 章 | 商业化产品 | 企业自研系统 |
|---|---|---|
| 3 商业分析 | 完整做：市场 + 竞品 | 替换为：同类系统调研 + 痛点优先级排序 |
| 4 收益目标 | 营收 / 客户数 / 续费率 / NPS | ROI + 效率提升 + 采纳率 |
| 13 运营计划 | 获客 + 客户成功 + 续费 | 内部推广 + 培训 + 试点 |

- **0-1 新系统**：14 章完整生成。**迭代/模块级**：1-2 章简化、3 章可省、聚焦变更模块。
- **商业化 SaaS** 额外关注：LTV/CAC > 3、多租户隔离、配置化能力。

## 1. PRD 14 章结构

| 章 | 内容 | 一句话 |
|---|---|---|
| 1 | 项目背景 | 现状 → 问题 → 解决思路 → 决策依据 |
| 2 | 需求基本情况 | 谁提、谁用、场景、痛点、价值（六要素） |
| 3 | 商业分析 | 目标市场 + 竞品（商业化）/ 同类调研（自研） |
| 4 | 项目收益目标 | SMART 目标 + 验收标准 + 成功标准 |
| 5 | 项目方案概述 | 功能模块表 + 方案概述 + MVP 范围 |
| 6 | 项目范围 | 涉及系统 + 影响范围 + 不在本期 |
| 7 | 项目风险 | 前提假设 + 约束 + 风险清单（概率×影响×应对） |
| 8 | 术语和缩略语 | 全称 + 定义 |
| 9 | 参考文献 | 前后置文档 + 外部规范 |
| 10 | **功能需求** | 框架概述 + 需求详解 + 异常处理（见下） |
| 11 | 数据埋点 | 页面/行为/业务/AI 专项指标 |
| 12 | 角色和权限 | 角色定义 + 权限矩阵 + 安全约束 |
| 13 | 运营计划 | 上线计划 + 种子用户 + 数据闭环 + 版本路线 |
| 14 | 待决事项 | TBD 编号 + 负责人 + 决策时间 |

## 2. 第 10 章 · 功能需求（最核心）

### 10.1 产品框架概述（五张图）

| 图 | Mermaid 语法 | 必须包含 |
|---|---|---|
| 应用架构图 | `graph TB` + `subgraph` | 用户层 / 接入层 / 业务服务层 / 数据层 / 外部系统 |
| ER 数据模型 | `erDiagram` | 核心实体 + 关系基数 + 关键属性（PK/FK/状态） |
| 核心业务流程图 | `flowchart TD` | 主流程 + 分支 + 异常路径，关键节点着色 |
| 状态机图 | `stateDiagram-v2` | 正常 + 异常路径，`note` 标注约束 |
| 功能清单 | 表格 | 子系统 / 功能 / 各端支持 / 说明 |

- 业务型/交易型：ER 图必须完整（设计基石）。
- 每个有状态流转的实体都画一张状态机。
- 图后附明细表格补充（如状态机图 + 状态转换表）。

### 10.2 产品需求详解（每个模块三段式）

```
流程图 → 页面交互 → 业务规则
```

- **页面交互**用表格：查询条件表 + 列表字段表 + 操作按钮表。
- **业务规则**按五种类型分类：**事实、约束、触发条件、推论、计算**。

### 10.3 异常情况处理（至少五类）

网络异常、并发冲突、数据异常、误操作、业务异常 —— 每类给具体处理方案，不写「待补充」。

### AI 功能设计（如适用）

- **确定性-容错性四象限**：按任务确定性（高/低）× 容错性（高/低）选交互模式。
- **六脉神剑交互模式**：封装 API / CUI 嵌入 GUI / Chat / Copilot / 辅助填充 / 后台自动化。
- 必答：人机边界（哪步 AI 做、哪步必须人确认）、降级方案、监控指标。

## 3. 输出规范

1. **有信息则生成实质内容，信息不足标注 `[TODO: 需要补充什么]`，不编造**。
2. 结构化优先：表格、列表、Mermaid 优先于大段叙述。
3. 图表全用 Mermaid，不用 ASCII 伪图。
4. 方法论外显：关键章节用 `> 💡` 标注所用框架。
5. 逐章输出：每完成一章立即输出，不等全部写完。

## 4. 自检与缺口分析（阶段 4）

### 重大风险项快扫（R1–R8）

产品定位 / 核心业务流程 / ER 模型缺陷 / 角色权限 / 功能致命缺口 / 需求与业务脱节 / 合规风险 / SaaS 多租户。
（R3 仅业务型/交易型、R7 仅强监管、R8 仅商业化 SaaS，其余标「不适用」。）

### 14 维度快速扫描

业务分析质量 / 类型适配 / 定位合理性 / 场景与旅程 / 结构完整性 / 架构质量 / 数据建模 / 流程与角色 / 交互质量 / 商业分析深度 / MVP 策略 / 异常健壮性 / AI 功能质量 / 运营与跟踪。

### 待完善清单（三级）

```
🔴 必须补充（影响可评审性）→ 优先解决，阻塞立项评审
🟡 建议补充（提升质量）
🟢 可选完善（锦上添花）
```

每个待完善项写清：缺什么、为什么重要、怎么获取。
